# ADR-0035: SealedSecrets Controller Keys Backed Up Daily by a Scheduled GitHub Actions Workflow

**Status:** Accepted
**Date:** 2026-11
**Related:** [ADR-0034](./0034-backup-key-custody-and-weekly-escrow-check.md) (dedicated GitHub environment, two age recipients), [ADR-0033](./0033-offsite-backup-bucket-object-lock.md) (off-site bucket, credentials without delete right), [ADR-0011](./0011-spiffe-spire-workload-identity.md), [ADR-0017](./0017-no-swallowed-errors.md)
**Verified by:** `tests/backup/sealed-secrets-key.test.sh`, `tests/k8s/sealed-secrets-key-drill.sh`

## Context

The production secrets are SealedSecrets committed in `deploy/k8s/secrets/`. Only the private keys of the Sealed Secrets controller decrypt them, and those keys lived in the cluster only (Secrets labelled `sealedsecrets.bitnami.com/sealed-secrets-key` in `kube-system`). The total outage recovery of `docs/deployment/BACKUP_DR.md` started with "deploy the manifests from git", which fails on every SealedSecret in a new cluster (audit sauvegarde-restauration 2026-11-01, finding A5, issue #328).

`scripts/backup-sealed-secrets-key.sh` (export of every key, sealed with age for `BACKUP_AGE_RECIPIENTS`, copied to the off-site bucket) and `scripts/restore-sealed-secrets-key.sh` close the gap for one run. The question left was who runs the backup, and when. The controller creates a new key every 30 days and keeps the old ones: a key never backed up is lost with the cluster, together with every secret sealed with it. Automating the backup gives something the right to read private keys of the controller namespace. Four options were put to the project owner: operator procedure only, a step of `deploy.yml`, a CronJob in the cluster, a scheduled GitHub Actions workflow. The owner chose the scheduled workflow (issue #328, 2026-11-03).

## Decision

1. **Daily scheduled workflow** `.github/workflows/sealed-secrets-key-backup.yml` (03:30 UTC, also on demand) runs `scripts/backup-sealed-secrets-key.sh` against the production cluster, in the `backup-tools` image. A key renewed by the controller is off-site within 24 h, whether or not a deploy follows. Staging has no SealedSecret (plain development secrets) and is not backed up.
2. **Dedicated GitHub environment `sealed-secrets-key-backup`**, deployment branches restricted to the default branch, no required reviewer (it would block the schedule, as for ADR-0034). It holds the secret `SEALED_SECRETS_BACKUP_KUBECONFIG`, the put credentials of the off-site bucket (`BACKUP_S3_ACCESS_KEY_ID` / `BACKUP_S3_SECRET_ACCESS_KEY`, no delete right, ADR-0033) and the variables `BACKUP_AGE_RECIPIENTS`, `BACKUP_S3_*`, `SEALED_SECRETS_NAMESPACE`. The deploy jobs never receive this kubeconfig; this job never receives the deploy kubeconfig.
3. **The controller runs in its own namespace `sealed-secrets`**, never in `kube-system`. `scripts/install-sealed-secrets.sh` installs the upstream `controller.yaml` v0.27.1 (sha256 pinned) moved there by kustomize, with the namespace of `deploy/k8s/sealed-secrets/namespace.yaml` (Pod Security `restricted`). Nothing else is deployed in it: it holds the controller, its keys and the backup identity. Reason: RBAC cannot filter by label and the keys have random names, so the backup identity lists every Secret of the controller namespace. On k3s, the target cluster, `kube-system` also holds `k3s-serving` (private key of the API server serving certificate), the `<node>.node-password.k3s` Secrets (node registration passwords) and the Secrets of the bundled Helm charts: an identity there would carry all of them out of the cluster (review of PR #338). `scripts/sealed-secrets-backup-identity.sh` and `install-sealed-secrets.sh` refuse `kube-system`; `deploy.yml` refuses a production deploy when no controller runs in `sealed-secrets`; `kubeseal` and the sealing scripts pass `--controller-namespace sealed-secrets`. A controller already in `kube-system` is moved with its keys (`docs/deployment/sealed-secrets.md`, "Move the controller out of kube-system").
4. **Least-privilege cluster identity**, never an admin kubeconfig: `scripts/sealed-secrets-backup-identity.sh` creates in the controller namespace the ServiceAccount `sealed-secrets-key-backup`, a Role with the single rule `list` on `secrets` (what `kubectl get secret -l <label>` needs: no `get`, `watch`, write, other resource or namespace), its RoleBinding and a token Secret, and prints the kubeconfig on stdout, piped straight into the GitHub secret. `--rotate` replaces the token. The kind drill checks the rights with `kubectl auth can-i` (nothing in `kube-system`), lists what the identity actually reads (the keys and its own token, nothing else, or the drill fails) and runs the real backup with this identity.
5. **Handling of the kubeconfig in the job**: written to a tmpfs, mode 600, never in an argument or a log, passed to the container by file, deleted in an `always()` step. Production rules apply: `BACKUP_MIN_RECIPIENTS=2` (operator + escrow keys, ADR-0034), encryption and off-site copy mandatory.
6. **Failure is a run failure**: a missing secret or variable, an unreachable API server or bucket, no key found, age or the copy failing: exit 1, GitHub notifies on the failed scheduled run. Never a skipped backup.
7. **The operator procedure stays** for what the schedule does not see: right after a manual key renewal, a controller reinstall or a restore, and before sealing a secret, an operator may run the script (or trigger the workflow) instead of waiting for the next run.

## Alternatives Considered

| Alternative | Reason for Rejection |
| --- | --- |
| Operator procedure only | No new right or secret, but rests on discipline: an automatic renewal forgotten goes unnoticed. Not chosen by the project owner |
| Step of `deploy.yml` before the overlay is applied | No new right or secret, covers every secret deployed by the pipeline, but a renewal between two deploys waits for the next deploy. Not chosen |
| CronJob in the cluster (`db-backup` style, metrics and alerts) | Continuous coverage, but the job's pod holds both the right to list the key Secrets and the bucket credentials. Not chosen |
| Keep the controller in `kube-system` and document the wider scope | The identity would read the k3s API server serving key and the node passwords; the response to a leak would extend to the API server certificate, the node passwords and every other Secret of `kube-system`. The move costs one install script and a one-off migration |
| Admin kubeconfig of production in the environment | Simplest, but a leaked secret would give the whole cluster; the restricted ServiceAccount costs one script |
| `resourceNames` on the Role | Impossible: the controller names its keys `sealed-secrets-key<random>` |

## Consequences

- A production cluster credential is stored in GitHub. Whoever can read the `sealed-secrets-key-backup` environment secrets (a repository admin, a workflow change merged to the default branch, a compromise of GitHub) can list every Secret of `sealed-secrets`: the controller keys and the identity's own token, nothing else of the cluster. With the keys they can decrypt every SealedSecret of the repository. Accepted by the project owner (option 4 of issue #328). Response to a leak (`docs/deployment/sealed-secrets.md`): `--rotate` the identity token, renew the controller keys, reseal every secret with new values, back up the new keys. No other cluster credential is exposed, as long as nothing else is deployed in `sealed-secrets`. Mitigations: list-only identity in one namespace that holds nothing but the controller, dedicated environment restricted to the default branch, review on workflow changes, kubeconfig on tmpfs and deleted after each run.
- `kubeseal` defaults to `kube-system`: every manual seal passes `--controller-namespace sealed-secrets` (or `SEALED_SECRETS_CONTROLLER_NAMESPACE`).
- GitHub disables the `schedule` trigger of a public repository after 60 days without activity, and mails a failed scheduled run only to the last person who changed the cron. A disabled schedule produces no failed run: the backup can stop without any signal. Known limit (`BACKUP_DR.md`), shared with ADR-0034; check the date of the newest `sealed-secrets-key_*.yaml.age` during the quarterly operator-key check.
- The Kubernetes API server must be reachable from GitHub-hosted runners, as for `deploy.yml`. A private API server needs a self-hosted runner for this workflow.
- After a total outage the new cluster has no `sealed-secrets-key-backup` identity: the scheduled run fails until an operator runs `sealed-secrets-backup-identity.sh` on it and updates the secret. That failure is the intended reminder (`BACKUP_DR.md`, total outage recovery).
- One file of a few kilobytes per day in `<bucket>/sealed-secrets-key/`, kept at least 30 days by Object Lock; no lifecycle rule expires the prefix (about 2 MB a year). The newest file always holds every key.
- Until the environment and its secrets exist, the scheduled run fails every day: that is the intended signal, not noise to silence.
- No error is swallowed (ADR-0017).
