# ADR-0041: Least-Privilege Deploy Identities — Application and Cluster-Scope, Bounded Tokens

**Status:** Accepted
**Date:** 2026-11
**Related:** [ADR-0035](./0035-sealed-secrets-key-daily-backup-by-github-actions.md) (precedent: list-only identity made by a script), [ADR-0017](./0017-no-swallowed-errors.md)
**Verified by:** `tests/k8s/deploy-identity.test.sh`, `tests/k8s/check-cluster-rbac.test.sh`, `tests/k8s/check-overlays.mjs`, `tests/k8s/check-deploy-commands.mjs`

## Context

`deploy.yml` authenticated with one static kubeconfig per environment (`KUBECONFIG_STAGING` / `KUBECONFIG_PRODUCTION`, base64 in a GitHub environment secret), without OIDC or any short-lived identity. The same job creates namespaces, applies privileged DaemonSets, a CSIDriver and ClusterRoles (node-agents, SPIRE server), so the kubeconfig had to be cluster-admin. One leaked secret meant control of the production cluster (audit déploiement 2026-11-05, M11, issue #418).

Rendering the overlays shows that very little of what the deploy applies is cluster-scope: `Namespace`, the `ClusterRole` / `ClusterRoleBinding` of the SPIRE server, and in the node-agents overlay the `CSIDriver`, two ClusterRoles and their bindings. All the rest (Deployments, StatefulSets, CronJobs, Services, ConfigMaps, Secrets, Ingresses, NetworkPolicies, HPA/VPA, PDB, SealedSecrets, PVCs, namespaced Roles) lives in the application namespace.

## Decision

1. **Two identities, two secrets per environment**, made by `scripts/deploy-identity.sh app|cluster` with an admin kubeconfig, printed as a kubeconfig on stdout and piped into the GitHub secret (`KUBECONFIG_<ENV>_APP`, `KUBECONFIG_<ENV>_CLUSTER`, base64). The former single `KUBECONFIG_<ENV>` secret is no longer read.
   - **`deploy-app`**: Role `deploy/k8s/deploy-identity/app-role.yaml` in the application namespace only. It applies the overlay, runs migrations, the canary, the smoke test, the rollout and the rollback. No cluster-scope right, no other namespace.
   - **`deploy-cluster`**: ClusterRole `cluster-role.yaml` (namespaces; CSIDriver; get/list on CRDs, get on StorageClasses, IngressClasses and ClusterIssuers; get/list only on ClusterRoles and ClusterRoleBindings), a Role in the node-agents namespace (`node-role.yaml`) and a Role in the Sealed Secrets controller namespace (`get deployments` only, no Secret: ADR-0035 keys stay out of reach). Used by four steps only: "Apply cluster-scope objects", "Check sealed secrets" (CRD and controller), "Check cluster prerequisites" (`check-prereqs.sh`), "Apply SPIFFE node components".
2. **`deploy.yml` splits the rendered overlay** with `scripts/split-cluster-scope.sh`: the cluster-scope documents are applied with the cluster identity, the rest with the application identity. The namespace is created by the cluster step before any Secret is written.
3. **No `escalate`, no `bind`, no RBAC write at cluster scope.** The application identity holds the rights of the Roles it creates (backup-runner), so Kubernetes' own escalation check applies to it. The cluster identity only reads ClusterRoles and ClusterRoleBindings: `scripts/deploy-identity.sh cluster --environment <env>`, run with an admin kubeconfig, applies those of the overlays (`spire-server`, `spire-agent`, `promtail`). *Amended by [ADR-0056](./0056-infrastructure-metrics-exporters.md): also `prometheus-nodes` (`nodes`, `nodes/metrics`), and the node-agents identity deploys the node-exporter DaemonSet.* The identity neither holds their rights (`nodes/proxy`, `pods`, `tokenreviews`) nor can bind them to itself. An unchanged object makes `kubectl apply` a no-op; a release that adds or changes one stops the deploy at "Check overlay ClusterRoles" until an admin runs the script again. `tests/k8s/deploy-identity.test.sh` fails when `cluster-role.yaml` grants `bind`, `escalate`, `impersonate` or a write on (cluster)roles / (cluster)rolebindings. A new overlay object that needs more fails the deploy until the role files change in review.
4. **`tests/k8s/check-overlays.mjs` fails** when a kind of an overlay is missing from the role files, so a new resource cannot reach production through a deploy that cannot apply it. `tests/k8s/deploy-identity.test.sh` (stub `kubectl`, in CI) proves the app identity gets a namespaced Role and no ClusterRole, the token is bounded, `--revoke` works and the scope split loses no document. `tests/k8s/check-deploy-commands.mjs` (CI `k8s-overlays`) extracts the verb/resource of every `kubectl` command run with the app identity (`deploy-k8s.sh`, `run-migrations.sh`, namespaced `deploy.yml` steps) and fails when `app-role.yaml` does not grant it (canary needs `endpointslices` and `deployments/scale`). The CI `k8s` job proves the restricted path on kind (issue #482): after the N-1 deploy as admin (cluster bootstrap), `run-kind.sh upgrade` creates both identities with `scripts/deploy-identity.sh`, then every release step (migrations, overlay split with `split-cluster-scope.sh`, rollout, rollback, smoke, canary) runs with `KUBECONFIG` = `deploy-app` and `CLUSTER_KUBECONFIG` = `deploy-cluster`, and asserts that `deploy-cluster` gets Forbidden on a self-bind to `spire-agent` and `no` on `get nodes/proxy`, and that `deploy-app` gets `no` on `get secrets -n kube-system`. The restore scenario and `backup-inspector` stay admin.
5. **Bounded tokens**: `kubectl create token --duration` (default 168 h; the API server may cap it), never a permanent `service-account-token` Secret. Rotation is running the script again before expiry and replacing the secret; `--revoke` deletes the ServiceAccount, which invalidates every token issued so far at once (suspected leak).
6. **OIDC is the recommended target, not delivered here**: when the cluster provider can trust GitHub's OIDC issuer, map the token claims (`repo`, `environment`) to these two identities (RBAC subjects `User`/`Group` instead of ServiceAccounts) and delete the static secrets. It depends on the provider, outside the repository (`docs/deployment/DEPLOY.md`).
7. **Human settings** (documented, not enforceable by the repository): required reviewer on the `production` environment with the cluster secret scoped to it, and a second CODEOWNER on `/.github/`, `/deploy/` and `/deploy/k8s/secrets/` (today `@docteur-turboss` alone).

## Alternatives Considered

| Alternative | Reason for Rejection |
| --- | --- |
| Keep one admin kubeconfig | Simplest, but a leak means the whole cluster |
| One restricted identity with a ClusterRole covering everything | Same blast radius as the cluster identity for every step; the application steps never need cluster rights |
| `escalate` / `bind` on RBAC to let the identity grant anything | Equivalent to cluster-admin: it could bind itself to `cluster-admin` |
| `bind` limited by `resourceNames` to the three workload ClusterRoles, the identity creating their bindings | Rejected after review of PR #481: proven on kind, the identity binds `spire-agent` to its own ServiceAccount and gets `nodes/proxy` |
| The cluster identity holds the rights of the ClusterRoles it creates | Rejected after review of PR #479: the SPIRE agent ClusterRole grants `nodes/proxy get`, i.e. the kubelet API (`exec` in any pod of any node, the WebSocket handshake is a GET), which with `pods list` reaches every namespace |
| Permanent `service-account-token` Secret | A leak is valid until someone notices; the bounded token expires alone |
| OIDC only | Best option, but needs provider support that the repository cannot configure |

## Consequences

- **A leak of `KUBECONFIG_<ENV>_CLUSTER` is close to root on every node.** The identity cannot write RBAC at cluster scope, read Secrets or bind `cluster-admin`, but it deploys the node agents: it creates DaemonSets, ServiceAccounts and Roles in `trading-model-node`, a namespace with the `privileged` Pod Security profile. A DaemonSet of its choice there can run privileged with host mounts, or run as the `spire-agent` ServiceAccount (bound by the admin to `spire-agent`, hence `nodes/proxy`). What bounds it: four steps only, a token that expires (shorten `--duration` for production), the required reviewer on the `production` environment (decision 7). Removing the node agents from this identity (admin-applied, like the ClusterRoles) would close it, at the cost of an admin step on every release that changes them.
- A release that changes `spire-server`, `spire-agent` or `promtail` (ClusterRole or binding) needs an admin to run `scripts/deploy-identity.sh cluster --environment <env>` before the deploy (3.1.0: `prometheus-nodes`). Otherwise the deploy stops at "Check overlay ClusterRoles" (`deploy/k8s/scripts/check-cluster-rbac.sh`, issue #701), before any apply, with the missing or different objects and that command.
- The application secret, which every deploy uses, no longer carries those rights. Both secrets are readable by the same job: the split limits what a stolen token can do, not what a malicious workflow change can do. The reviewer and CODEOWNER settings above cover that.
- Tokens expire: a deploy after expiry fails at "Configure kubeconfigs" (`kubectl auth can-i`) before anything is applied. Renewal is a calendar task (`docs/deployment/DEPLOY.md`).
- Creating the identities in the clusters, the OIDC setup and the second CODEOWNER are human actions, out of scope of this change. Until the four new secrets exist, deploys fail at the first step.
- `cluster-info` is no longer used: it reads `kube-system`, which neither identity can.
