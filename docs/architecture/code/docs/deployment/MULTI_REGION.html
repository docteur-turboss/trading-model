Multi-Region Deployment

This document describes how to deploy the Trading Model platform across multiple geographic regions / datacenters to achieve high availability, disaster recovery, and low-latency service-to-service communication.

Key Components

1. Registry Shared Through Redis

The discovery-server keeps its registry in Redis whenever Redis is configured (ADR-0023); createDiscoveryApp (services/discovery-server/src/config/container.ts) picks the store:

Store Selected when Use case
InstanceStore neither REDIS_SENTINELS nor REDIS_URL Development, single replica
RedisInstanceStore REDIS_SENTINELS (else REDIS_URL) Staging, production, N replicas

Instance tokens follow the same rule (RedisTokenStore). Keys live under the fixed prefix trading-model:discovery: (not configurable). Every replica connected to the same Redis shares the registry and accepts any heartbeat:

environment:
  REDIS_SENTINELS: redis-sentinel-0.redis-sentinel-headless:26379,redis-sentinel-1.redis-sentinel-headless:26379
  REDIS_SENTINEL_MASTER_NAME: mymaster
  # or, single node: REDIS_URL: redis://redis:6379
  SIGNING_SECRET: <shared by every replica, required in production>

2. Multi-URL Discovery Client

Each service client (via @trading-model/address-manager) can be configured with multiple discovery server URLs for failover:

# Single URL (legacy, backwards-compatible)
ADDRESS_MANAGER_URL=https://discovery-server:3000

# Multiple URLs (JSON array – tried in order)
ADDRESS_MANAGER_URLS='["https://ds-us-east:3000","https://ds-eu-west:3000"]'

The client tries each URL sequentially:

  1. Primary discovery server
  2. Secondary (on failure / timeout)
  3. Tertiary, etc.

3. Region-Aware Service Discovery (not implemented)

There is no region-aware routing. discovery-server neither receives nor stores a region at registration, and has no region-filtered route: every lookup returns the instances of every region. The address-manager used to query a /services/:name/region/:regionName route that never existed (a 404 on every lookup, then a fallback to the plain lookup); that call and the REGION variable were removed on 2026-10-31, and tests/contract/discovery-routes.spec.ts now fails if the client calls a route discovery does not serve.

Region-aware routing would need a region in the registration payload and REGISTER_SCHEMA, stored with the instance, a filtered route in DISCOVERY_API and a client lookup that uses it.

4. Token Recovery

Instance tokens are HMAC-signed with SIGNING_SECRET and stored in Redis, so a discovery-server restart or another replica keeps accepting them. When a token is unknown (Redis lost, in-memory registry restarted), the heartbeat gets a 401 and the address-manager registers the instance again immediately.

Configuration

Discovery Server

# docker-compose.override.yml (per-region)
services:
  discovery-server:
    environment:
      - REDIS_SENTINELS=redis-sentinel-0:26379,redis-sentinel-1:26379,redis-sentinel-2:26379
      - REDIS_SENTINEL_MASTER_NAME=mymaster
      - SIGNING_SECRET=${SIGNING_SECRET}

Service Clients

services:
  financial-scraper:
    environment:
      - ADDRESS_MANAGER_URLS=["https://ds-us-east:3000","https://ds-eu-west:3000"]
      - REGION=us-east-1

Infrastructure Requirements

Redis With Sentinel

The registry needs one Redis master reachable by every discovery-server replica. The services speak Sentinel (REDIS_SENTINELS), not Redis Cluster:

  • Minimum: 1 master + 2 replicas, 3 sentinels (deploy/k8s/infra/redis.yaml, started by deploy/k8s/infra/redis-ha.sh), AOF on
  • Recommended: Redis 7+ with TLS and password authentication (REDIS_PASSWORD)
  • A single registry for all regions means one master in one region: the other regions write across the inter-region link

Cross-Region Networking

  • Low-latency links between regions (AWS Direct Connect / Azure ExpressRoute)
  • SVIDs valid across regions (SPIRE trust bundle + cross-region SPIRE Server sync)
  • Firewall rules allowing inter-region traffic on discovery ports (3000)

Database Replication

Database Replication Strategy
MySQL Primary-replica cross-region replication
MongoDB Replica set with members in multiple regions

Deployment Phases

Phase 1: Single Region with Redis

  1. Deploy a Redis cluster in one region
  2. Set REDIS_SENTINELS (or REDIS_URL) and SIGNING_SECRET on the discovery-server
  3. Verify all services register and discover each other

Phase 2: Second Region

  1. Deploy a second infrastructure stack in a new region
  2. Connect the second discovery-server to the same Redis cluster
  3. Configure ADDRESS_MANAGER_URLS on all services to include both regions

Phase 3: Multi-Region Active-Active

  1. Implement region-aware routing (section 3: nothing exists today)
  2. Verify it
  3. Test failover by disabling one region

Disaster Recovery

Scenario: US-East region failure

When the us-east-1 discovery-server or services become unreachable:

  1. Client heartbeats fail → instances are not removed from Redis (they keep their last heartbeat timestamp)
  2. Services in eu-west-1 continue heartbeating normally
  3. When a service in eu-west-1 calls findService(), it gets the instances of every region (no region-aware routing, section 3) and takes the first one listed; if it fails its health check the lookup fails and is retried

Recovery after region restart

When us-east-1 comes back:

  1. Services re-register with the same instanceId
  2. Tokens are still in Redis (shared SIGNING_SECRET): heartbeats resume without re-registration; an unknown token gets a 401 and the instance registers again
  3. The registry in Redis already contains the instances
  4. Heartbeats resume and TTL is refreshed
