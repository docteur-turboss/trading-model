Backup & Disaster Recovery

Overview

This document defines the backup strategy, disaster recovery procedures, and restore verification for the trading-model platform.

Status (2026-10-28): a backup counts only once it has been restored. Both sets of scripts are restored for real by CI:

  • Kubernetes: every run of the CI k8s job backs up with the db-backup CronJob, stops the MongoDB writers, destroys data (the real audit and dlq databases, drill markers, the market_candles table, the SPIRE server volume) and restores it with scripts/restore-k8s.sh (tests/k8s/run-kind.sh, verify_backup). The audit trail written by audit-logger from the live flow must come back whole: same events, same hashes, hash chain verified (tests/backup/audit-chain.js), then extended by audit-logger after the restore.
  • Docker: backup-test.yml (weekly and on changes to the scripts) deletes the containers and their volumes and restores them with scripts/restore.sh (tests/backup/compose-restore-drill.sh). Last run passed on 2026-10-28.

Known limits are listed at the end of this document.

Redis discovery-server, dlq-service, readiness Low Not backed up Rebuilt

Redis only holds derived state: instance registrations and tokens (services register again), the DLQ retry queue (rebuilt from MongoDB by dlq-service) and readiness keys. A day-old snapshot would restore stale tokens and queue entries, so Redis is not backed up in Kubernetes. The Docker scripts still dump it (single node). With REDIS_APPENDONLY=yes Redis starts from its append-only file and would ignore a restored dump.rdb: scripts/restore.sh loads the snapshot in a throwaway server on the same volume and rewrites the AOF from it before starting Redis again.

Automated Backup System

Kubernetes

The CronJob db-backup (deploy/k8s/jobs/backup-cronjob.yaml) runs daily at 2:00 AM with the backup-tools image (deploy/backup: kubectl, age, rclone) and the scripts from the backup-scripts ConfigMap.

# Manual run
kubectl create job --from=cronjob/db-backup db-backup-manual

The job fails (and its alerts fire) when:

  • no age recipient is configured (BACKUP_REQUIRE_ENCRYPTION=true);
  • no off-site store is configured, or the copy fails (BACKUP_REQUIRE_OFFSITE=true): a single volume is not a backup;
  • any component cannot be found or dumped (missing pod, no MongoDB primary...).

Docker

# Full backup (all components)
bash scripts/backup.sh

# Selective backup
bash scripts/backup.sh --components mongodb,mysql

# Dry-run (preview without executing)
bash scripts/backup.sh --dry-run

# Encrypted (age public key; refuse to run without it)
BACKUP_AGE_RECIPIENTS=age1... BACKUP_REQUIRE_ENCRYPTION=true bash scripts/backup.sh

# With off-site upload (encrypted files only)
BACKUP_AGE_RECIPIENTS=age1... BACKUP_S3_BUCKET=s3://my-bucket/backups bash scripts/backup.sh

Docker has no scheduler: schedule backup.sh with the host's cron if a compose stack holds data that matters.

Components Backed Up

Component Method Consistency
MongoDB dlq and audit (one dump per replica set, from its primary) mongodump --gzip --oplog --archive Point-in-time (end of the dump)
MongoDB (Docker: message-manager, audit-logger, dlq) mongodump --gzip --archive (standalone) Per collection
MySQL, every non-system database (financial_scraper, spire) mysqldump --databases … --single-transaction --set-gtid-purged=OFF Transaction-consistent snapshot
Trainer checkpoints tar czf of /data/checkpoints/ Filesystem snapshot
SPIRE CA keys, K8s (keys.json) read through the spire-entries sidecar (read-only mount) File copy; datastore is in MySQL
SPIRE server, Docker (/run/spire/data) docker cp of the whole directory, server paused keys.json + SQLite datastore together
Redis (Docker only) BGSAVE, wait for LASTSAVE, stream dump.rdb Fork-consistent

The mysql system schema is not dumped (it cannot be restored over a running server); users come from the deployment (MYSQL_ROOT_PASSWORD, MYSQL_USER). Dumps carry no GTID statement, so a restore goes through the binlog to the replicas. Older dumps taken with GTID statements (before 2026-10-28) are filtered at restore time (strip_gtid in scripts/backup-lib.sh); without the filter they fail with ERROR 3546 GTID_PURGED.

Every dump is streamed through age before it touches a disk (files suffixed .age). Keys, restore and monitoring: Encryption at Rest.

Off-site Storage (mandatory in Kubernetes)

BACKUP_S3_BUCKET copies each run's encrypted files to any S3-compatible store (rclone, or the aws CLI as fallback). Only encrypted files leave: without BACKUP_AGE_RECIPIENTS the copy is refused.

In Kubernetes the Secret trading-model-backup-s3 holds BACKUP_S3_BUCKET, AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_REGION, and for a non-AWS store (MinIO on another VPS, Backblaze B2, Scaleway, OVH...) S3_ENDPOINT and S3_PROVIDER. deploy.yml writes it from the GitHub environment: variables BACKUP_S3_BUCKET, BACKUP_S3_REGION, BACKUP_S3_ENDPOINT, BACKUP_S3_PROVIDER, secrets BACKUP_S3_ACCESS_KEY_ID, BACKUP_S3_SECRET_ACCESS_KEY. Without them, an existing Secret (e.g. a SealedSecret) is kept. Enable versioning or object lock on the bucket: the job only adds files, retention off-site is the bucket's lifecycle rule.

Retention

  • backup-data volume: 30 days (RETENTION_DAYS, files pruned by prune_old)
  • Off-site: the bucket's lifecycle rule

Monitoring

backup-k8s.sh writes /backups/metrics/backup.prom, served by backup-metrics-exporter and scraped by Prometheus (job backup-metrics).

Alert Fires when

Restore Procedures

Encrypted backups (*.age) need the age private key: BACKUP_AGE_IDENTITY=~/backup-key.txt in front of any restore command below. Manual decryption: age -d -i backup-key.txt <file>.age.

Both restore scripts exit 1 if any step fails. Stop the writers first (kubectl scale deployment --replicas=0 for financial-scraper, financial-scraper-collector, dlq-service, audit-logger, message-manager) when restoring after data corruption: a restore running next to live writers can collide with their inserts.

After a restore of the audit database, AuditChainBroken fires when anchors were written after the backup (ADR-0027): those events are lost. Once the restore is explained, acknowledge the loss (runbook-audit-chain-broken).

Kubernetes

restore-k8s.sh needs namespace admin rights: exec into the databases, stop and start the SPIRE server, create a helper pod. Order matters: MySQL (which holds the SPIRE datastore) before SPIRE.

From a workstation, with the backup files copied locally:

BACKUP_DIR=./backups K8S_NAMESPACE=trading-model BACKUP_AGE_IDENTITY=~/backup-key.txt \
  bash scripts/restore-k8s.sh                      # mongodb,mysql,checkpoints,spire
bash scripts/restore-k8s.sh --timestamp 2026-10-01_020000 --components mongodb

Or inside the cluster, next to the backup-data volume: a pod running backup-tools with the backup-scripts ConfigMap at /scripts and backup-data at /backups (as tests/k8s/restore-runner.yaml does), the private key passed on stdin:

kubectl exec -i -n trading-model restore-runner -- sh -c \
  'umask 077 && cat > /tmp/id && BACKUP_AGE_IDENTITY=/tmp/id K8S_NAMESPACE=trading-model \
   bash /scripts/restore-k8s.sh; rc=$?; rm -f /tmp/id; exit $rc' < ~/backup-key.txt

What it does:

  • MongoDB: finds the writable primary of each replica set and runs mongorestore --drop --oplogReplay there (secondaries follow).
  • MySQL: pipes the dump (GTID statements filtered) into the pod behind mysql-primary, with the container's own root password.
  • SPIRE: scales spire-server to 0, writes keys.json into its volume from a helper pod (RESTORE_HELPER_IMAGE, default backup-tools) running as the server's user, scales it back and checks spire-server healthcheck.

Docker

bash scripts/restore.sh                                   # latest, all components
bash scripts/restore.sh --timestamp 2025-01-01_120000
bash scripts/restore.sh --components mongodb,mysql
bash scripts/restore.sh --dry-run

SPIRE: the server is stopped and its whole data directory (data_*.tar: CA keys + SQLite datastore) is written back; backups taken before 2026-10-28 only hold keys_*.json and restore the keys alone.

SPIRE CA restore and SVIDs

Restoring the CA keys together with the datastore of the same backup brings back the trust bundle unchanged: SVIDs issued before the incident stay valid. SVIDs issued by a CA generated after the loss (between the incident and the restore) are signed by a key no longer in the bundle: restart the spiffe-helper sidecars, or wait for their rotation, if a workload rejects peers after the restore. The CI drill checks that Prometheus scrapes every target over mTLS after the restore.

Disaster Recovery

Failure Scenarios

Scenario Impact Recovery Action
Single container crash Degraded service Docker auto-restart / Kubernetes restart
Node failure Degraded / outage Replica sets and StatefulSets reschedule; restore if a volume is lost
Data corruption Data loss Stop the writers, restore from the latest backup
Full region failure Complete outage Deploy to secondary region (see MULTI_REGION.md), restore from the off-site copy
Secrets leak Security breach Rotate all secrets, rotate SPIRE trust bundle / SVIDs

Recovery Steps for Total Outage

  1. Provision replacement hosts, deploy the manifests from git (deploy.yml)
  2. Fetch the latest encrypted backups from the off-site bucket
  3. Restore the databases: MongoDB → MySQL (incl. SPIRE spire)
  4. Restore the SPIRE CA keys (keys.json), which restarts the SPIRE server
  5. Restore the trainer checkpoints
  6. Verify health endpoints, service registration in discovery-server and the Prometheus targets (all up means mTLS works)

Recovery Verification

# Check all services are registered (through edge-proxy → gateway)
curl -s http://localhost:8449/v1/discovery-server/services -H "x-api-key: <AUTH_TOKENS value>"

# Check core service health (mTLS via SPIRE SVIDs, run inside a service container)
for svc in discovery-server message-manager api-gateway; do
  docker compose exec -T "$svc" sh -c \
    'curl -sk --cert /run/spire/svid/svid.pem --key /run/spire/svid/svid_key.pem https://localhost:3000/ping'
done

Known Limits

  • No point-in-time recovery between dumps: binlogs are not archived, the MongoDB oplog is only captured during the dump. RPO is 24 h.
  • Docker stack: no scheduler, no backup metrics scraped, Redis without persistence (derived state only). Compose is a development stack.
  • No business-level validation after a restore beyond the CI drill: check the latest market_candles by hand after a real restore. The audit trail can be checked: mongosh --eval "const AUDIT_DB = 'audit'; $(cat tests/backup/audit-chain.js)" on the audit primary (broken must be null). Events stored before 2026-10-31 hold correlationId: null where their hash saw no field; the verifier drops that null (audit-logger never hashes one), so they verify too.
