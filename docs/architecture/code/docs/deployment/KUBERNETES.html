Kubernetes Deployment Guide

Overview

This guide covers deploying the Trading Model platform on Kubernetes. The K8s manifests are located in deploy/k8s/ and are designed to be applied with kubectl or Kustomize.

Prerequisites

  • Kubernetes cluster 1.28+ (tested with AKS, EKS, GKE, k3s)
  • kubectl configured with cluster access
  • Ingress controller (nginx-ingress recommended)
  • cert-manager for TLS certificate management
  • Prometheus Operator (optional, for enhanced alerting)
  • Default StorageClass for the ReadWriteOnce PVCs (MySQL, MongoDB, Redis, Prometheus, Grafana, Loki, SPIRE)
  • A ReadWriteMany StorageClass named rwx-csi (NFS, EFS, Azure Files...) for the trainer checkpoints PVC (trainer-checkpoints-pvc)
  • A CNI that enforces NetworkPolicies
  • One environment per cluster: the node agents (SPIRE agent, promtail) serve a single application namespace
  • Self-hosted nodes: data disk encrypted with LUKS2 + Clevis/Tang (deploy/host/, see Encryption at Rest)
  • An age public key in the GitHub environment variable BACKUP_AGE_RECIPIENTS: the db-backup CronJob refuses to write unencrypted backups

Directory Structure

deploy/k8s/
  base/                       # Kustomize base overlay
    namespace.yaml            # trading-model namespace (Pod Security: restricted)
    kustomization.yaml        # Resource list
  config/                     # ConfigMaps per service (+ HPA, PDB, NetworkPolicy, ServiceAccount)
  secrets/                    # Kubernetes Secrets (placeholder values)
  services/                   # Deployments + Services per microservice
  infra/                      # Infrastructure: MySQL, MongoDB, Redis, OTel, Jaeger, Prometheus, Grafana, Loki, SPIRE server
  node-agents/                # Namespace trading-model-node (privileged): SPIRE agent, SPIFFE CSI driver, promtail
  overlays/<env>/             # Application overlay per environment
  overlays/<env>/node-agents/ # Node agents pointed at that environment's namespace
  ingress/                    # Ingress rules: public API (→ edge-proxy), Grafana
  monitoring/                 # PrometheusRules for alerting
  scripts/                    # deploy-k8s.sh, run-migrations.sh

Quick Start

1. mTLS via SPIRE (default)

mTLS identities are issued by SPIRE (ADR-0011) — mandatory and enabled by default in the base kustomization. Every workload runs a spiffe-helper sidecar that writes its SVID into /run/spire/svid (svid.pem, svid_key.pem, bundle.pem) and TLS_*_PATH points at those files. No manual certificate generation or trading-model-tls secret is required for services:

# 1. Node agents (SPIRE agent, SPIFFE CSI driver, promtail), once per cluster
kubectl kustomize deploy/k8s/overlays/staging/node-agents | kubectl apply -f -
# 2. Application overlay (jobs/ packages a script from outside its directory)
kubectl kustomize --load-restrictor LoadRestrictionsNone deploy/k8s/overlays/staging | kubectl apply -f -
# 3. Schema (scripts/migrations) once MySQL is up
bash deploy/k8s/scripts/run-migrations.sh trading-model-staging

The CI k8s job runs the same sequence on kind, then the two gates of deploy.yml (deploy-k8s.sh smoke-test, and the canary on api-gateway with traffic through edge-proxy, which must also fail without traffic), and checks the stack (tests/k8s/run-kind.sh). The deploy.yml workflow runs these steps (migrations go before the rollout, or right after the overlay on a first deploy, when MySQL does not exist yet).

Public API path: the nginx ingress controller (installed outside this repo) terminates TLS for api.trading-model.example.com and forwards plain HTTP to the edge-proxy, which calls the api-gateway over mTLS with its own SPIRE SVID (ADR-0018). The controller needs no client certificate, and no request reaches a service without going through the gateway (auth, rate limit per API client).

2. Configure secrets

Edit deploy/k8s/secrets/ to set production values, then:

# Apply secrets (or use SealedSecrets/SOPS for production)
kubectl apply -k deploy/k8s/secrets/

For production, use SealedSecrets or an external secrets operator:

# Seals every production secret with the cluster's controller key (writes
# deploy/k8s/secrets/*-sealed.yaml; commit them). deploy.yml refuses to deploy
# production while a placeholder (AgCHANGE_ME...) is left.
bash scripts/init-sealed-secrets.sh

See Sealed Secrets guide for detailed setup, key rotation, and migration instructions.

3. Deploy all resources

# Using the deploy script
./deploy/k8s/scripts/deploy-k8s.sh apply

# Or directly with Kustomize
kubectl apply -k deploy/k8s/

# Verify deployment
./deploy/k8s/scripts/deploy-k8s.sh status

4. Run smoke tests

./deploy/k8s/scripts/deploy-k8s.sh smoke-test

Deployment Strategy

Standard deployment

./deploy/k8s/scripts/deploy-k8s.sh apply <service-name>

Canary deployment

# Deploy to 10% of instances first, monitor, then full rollout
./deploy/k8s/scripts/deploy-k8s.sh canary <service-name> 10

Rollback

# Rollback to previous version
./deploy/k8s/scripts/deploy-k8s.sh rollback <service-name>

# Rollback to specific revision
kubectl rollout history -n trading-model deployment/<service-name>
./deploy/k8s/scripts/deploy-k8s.sh rollback <service-name> <revision>

Infrastructure Components

MySQL

  • StatefulSet (MySQL 8.4) with group replication (single primary), bootstrapped by the mysql-cluster-init Job; per-pod server_id / local address passed as mysqld arguments
  • 20Gi PVC per replica
  • Schema from the db-migrate Job (scripts/migrations, run-migrations.sh), the same migrations as compose: no second copy of the schema
  • PodDisruptionBudget: minAvailable 1

MongoDB (Replica Set)

  • StatefulSet with 3 replicas (Community edition)
  • 20Gi PVC per replica
  • Replica set initialized via an idempotent init Job (members: the pods that answer, so scaled-down overlays work)
  • Headless service for DNS-based discovery
  • PodDisruptionBudget: minAvailable 2

Redis + Sentinel

  • Redis primary: StatefulSet, 1 replica, 10Gi PVC
  • Redis sentinel: StatefulSet, 3 replicas, anti-affinity
  • Sentinel configuration via ConfigMap
  • Services for primary and sentinel discovery

Observability Stack

  • OpenTelemetry Collector: 2 replicas, accepts OTLP HTTP, exports metrics on :8888 (its own telemetry is off: it would bind the same port), health on :13133
  • Jaeger: 1 replica, OTLP gRPC receiver
  • Prometheus: StatefulSet, 50Gi PVC, 30d retention, mTLS scrape
  • Grafana: StatefulSet, 10Gi PVC, Prometheus + Jaeger datasources
  • Loki + promtail: promtail is a node agent (trading-model-node) tailing /var/log/pods of the application namespace
  • Alertmanager: credentials read from files (slack_api_url_file, routing_key_file, url_file) of the alertmanager-credentials Secret, written by deploy.yml from the GitHub environment (production refuses to deploy without a Slack webhook and a dead man's switch). Alertmanager expands no environment variables. See Alerting

Workload Identity (SPIRE)

Per ADR-0011 the platform uses SPIFFE/SPIRE instead of the former in-house CA:

  • SPIRE Server: Deployment in the application namespace (MySQL datastore, spire database). Config rendered with -expandEnv (the official images have no shell). The k8sbundle notifier publishes the trust bundle into the spire-bundle ConfigMap of trading-model-node
  • SPIRE Agent: DaemonSet in trading-model-node (hostPID + hostNetwork) with the k8s_psat node attestor (projected token, audience spire-server, bootstrapped from spire-bundle) + k8s workload attestor
  • SPIFFE CSI driver: DaemonSet in trading-model-node exposing the agent socket to pods as a csi.spiffe.io ephemeral volume. The application namespace enforces the restricted Pod Security profile, which forbids hostPath: the agent and the driver need the host and live in the privileged node namespace
  • Registration: the spire-entries sidecar of the server pod (ghcr.io/trading-model/spire-tools, built from deploy/spire/ by the release) reconciles the agent node alias and one workload entry per service account (spiffe://trading-model.local/ns/<namespace>/sa/<sa>) at start and every 10 minutes
  • Consumption: spiffe-helper sidecars (config file only: ConfigMap spiffe-helper-config) write svid.pem/svid_key.pem/bundle.pem consumed via the standard TLS_* paths (/run/spire/svid) — part of the base kustomization, applied to all workloads (services, prometheus, blackbox-exporter)
  • Metrics: the prometheus identity may only GET /metrics on the services

Security

Network Policies

All services have NetworkPolicies that restrict ingress/egress:

  • Ingress: only from pods of the same namespace (podSelector: {}, so overlays in other namespaces such as trading-model-staging work), except api-gateway (ingress controller) and edge-proxy (any namespace, port 8080). edge-proxy may only egress to the api-gateway
  • Egress: only to required infrastructure ports, plus the shared allow-dns-and-telemetry-egress policy (cluster DNS, OTLP to the collector) for the components with an egress policy. It lists them explicitly: a policy selecting a pod for Egress isolates its egress, so selecting every pod would cut the others (Redis, Mongo, Grafana...) down to DNS + OTLP
  • External egress: only for financial-scraper (Binance API)

Encryption at Rest

  • Node data disks: LUKS2, unlocked at boot by Clevis through Tang servers hosted on other machines (or the TPM2 of a home PC): deploy/host/
  • Backups: every dump encrypted with age while written (backup-tools image, BACKUP_REQUIRE_ENCRYPTION=true, recipients in the backup-encryption ConfigMap written by deploy.yml); only .age files go off-site

Details, threat model and operations: Encryption at Rest.

Secrets Management

  • Development: Kubernetes Secrets with generator values
  • Production: Use SealedSecrets, External Secrets Operator, or Vault
  • TLS certificates: cert-manager ClusterIssuer manages only the public ingress certs (api-gateway, Grafana). Inter-service mTLS is entirely SPIRE-based (ADR-0011): SVIDs issued by SPIRE Server, consumed via spiffe-helper sidecars — no manual TLS secrets for internal traffic.

Service Accounts

Each service has a dedicated ServiceAccount with automountServiceAccountToken: false (no pods need K8s API access).

Known Limitations (current version)

  1. Encryption at rest lives below the databases — the community editions run without database-level encryption (the former options were MariaDB-only and MongoDB Enterprise-only and crashed both databases). Data disks are encrypted on the hosts (LUKS2 + Clevis/Tang, deploy/host/) and backups with age: see Encryption at Rest. Nothing in the cluster can tell whether the nodes' disks are encrypted: run deploy/host/check-encryption.sh on each node
  2. MySQL group replication is bootstrapped on the first member only; the other members' join is not automated
  3. Grafana is single-instance — dashboard provisioning but no HA
  4. Jaeger is single-instance — in-memory storage (not Elasticsearch/Cassandra)
  5. Off-site backups need a bucket — the db-backup CronJob copies the age-encrypted files with rclone once the trading-model-backup-s3 secret exists; without it they stay on the in-cluster backup-data volume
  6. Pod Security admission — the application namespace enforces restricted; trading-model-node is privileged (node agents)
