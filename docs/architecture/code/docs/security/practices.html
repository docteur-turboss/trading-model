Security Standards

Why

Protect the infrastructure, guarantee data integrity, and ensure robust authentication between services. This project interacts with real financial markets — security flaws can lead to financial loss.

mTLS (Mutual TLS)

All services communicate via HTTPS with mTLS enabled. Each service authenticates with its own SPIFFE identity (ADR-0011) and verifies the peer's SVID.

Workload Identity (SPIRE)

mTLS identities are issued by SPIRE: spiffe-helper sidecars fetch each service's SVID and write it to /run/spire/svid (svid.pem, svid_key.pem, bundle.pem), consumed via TLS_*_PATH. No manual certificate generation is required.

Each SVID carries a SPIFFE URI SAN (spiffe://trading-model.local/ns/<namespace>/sa/<service>) — one identity per service (8 services):

  • admin-interface
  • api-gateway
  • audit-logger
  • discovery-server
  • dlq-service
  • financial-scraper
  • message-manager
  • trader-trainer

mTLS Configuration in the Service

import { createSecureServer } from '@trading-model/server-utils/adapters/inbound/create-secure-server';
import { env } from '../config/env';

export function createServer() {
  return createSecureServer({
    port: env.PORT,
    tls: {
      key: env.TLS_KEY_PATH,
      cert: env.TLS_CERT_PATH,
      ca: env.TLS_CA_PATH,
    },
    routes: app => {
      /* ... */
    },
  });
}

Token Authentication (HMAC)

Each service instance uses an HMAC-SHA256 token passed in the x-instance-token header.

  • Token generated by discovery-server upon registration
  • Validated by each service receiving a request
  • Renewed periodically (TTL)
// Validation middleware
app.use((req, res, next) => {
  const token = req.headers['x-instance-token'];
  if (!token || !validateHmacToken(token)) {
    return res.status(401).json({ error: 'Invalid token' });
  }
  next();
});

Environment Variable Validation (Zod)

All environment variables are validated at startup via Zod. The application fails immediately (fail-fast) if a variable is missing or invalid.

import { z } from 'zod';

const envSchema = z.object({
  NODE_ENV: z.enum(['development', 'production', 'test']),
  PORT: z.coerce.number().default(3000),
  TLS_KEY_PATH: z.string().min(1),
  TLS_CERT_PATH: z.string().min(1),
  TLS_CA_PATH: z.string().min(1),
});

export const config = envSchema.parse(process.env);

Loading Order (Priority)

1. .env.local (if exists) - NOT committed
2. .env.{NODE_ENV}.local - NOT committed
3. .env.{NODE_ENV} - Committed (production values sanitized)
4. .env - Committed
5. .env.example - Reference only

Dependencies

  • bun audit: Run regularly to detect known vulnerabilities
  • Dependabot: Enabled on the repository — automatic PRs for security updates
  • Quick review and merge of Dependabot PRs (high priority)
  • No dependencies with known vulnerabilities in production

Reporting a Vulnerability

Refer to SECURITY.md — the root security document contains:

  • Private reporting procedure (email: docteur.turboss@gmail.com)
  • Prioritized vulnerability categories (RCE, auth bypass, mTLS, order manipulation, etc.)
  • Response time commitments (< 72h acknowledgement)
  • Responsible disclosure policy

High Priority Vulnerability Categories

  • Remote code execution (RCE)
  • Authentication or authorization bypass
  • mTLS misconfiguration or certificate validation issues
  • Order execution manipulation
  • Risk limit bypass
  • Model poisoning or training data manipulation
  • Central monitor compromise
  • Secret leakage (API keys, certificates, credentials)
  • Supply chain vulnerabilities

DO NOT

  • Open a public issue for a security vulnerability
  • Commit keys, tokens, certificates, or passwords
  • Disable mTLS validation in development
  • Use weak cryptographic algorithms
