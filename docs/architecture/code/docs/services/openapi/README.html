OpenAPI Specifications

api-gateway.yaml describes the external API: the gateway's own routes and every route it proxies as /v1/<service>/<route>.

internal/<service>.yaml describes the service-to-service routes of a service (discovery registration and leases, message-manager publish and subscriptions, the broker callback POST /message of each subscriber, the trainer's model weights download, ADR-0022). The gateway never exposes them; they are called in-cluster over mTLS.

Generated, never edited

The spec is generated by scripts/api-contract.mjs from the Express route declarations of the services (TypeScript AST), including the routes mounted by shared packages (/ping and /health/ready from server-utils, /status from address-manager, the broker callback POST /message).

bun run api:write   # regenerate after adding, renaming or removing a route
bun run api:check   # CI + pre-push: fails when the committed spec is stale

Infrastructure routes (/metrics, /health, /health/ready, /ping, /status) and service-to-service routes (discovery registration and heartbeats, broker callbacks and subscriptions) are left out of the spec. The lists live at the top of the script.

What else api:check verifies

  • Documentation → code: gateway URLs (/v1/<service>/...) in any Markdown file, and the routes listed in docs/services/<service>.md (`METHOD /path` mentions and route tables), must exist.

There is no frontend consumer to check since admin-interface was removed (ADR-0018); a new frontend must come back with its calls checked here, with no known gap.

Entries already broken when the check was introduced are listed, with the reason, in scripts/api-contract-known-gaps.json. A new broken entry fails the check, and so does a listed entry that has been fixed or removed: the list can only shrink.

Schemas (ADR-0021)

Routes mounted from a registry entry (mountRoute(router, REGISTRY.key, ...), src/adapters/inbound/[http/]api-routes.ts of the service) are described from their Zod schemas: path and query parameters, request body (input side of the schema) and each response status (output side), with the shared ErrorResponse component and the signed-request headers as security schemes. The script loads the registries from the workspace sources with bun, so they must stay free of side effects (schemas only).

Every public route and every service-to-service route is mounted from an entry: api:check fails on a route of either kind that is not, on an entry that is never mounted, and on a stale or leftover spec. The schemas list of scripts/api-contract-known-gaps.json is empty and may only stay so.

The registries are loaded from the package sources, not their dist/: the scripts run with --tsconfig-override=scripts/api-contract.tsconfig.json, whose paths map each @trading-model/<pkg>/* to packages/<pkg>/src/* (api:check refuses to run otherwise, and fails when a package is missing from the file). Always go through bun run api:check / api:write. On Windows, bun 1.3 prints an "Internal error: directory mismatch" line for the override: harmless, the check result and exit code are right. The responses themselves are checked in the services' route specs (responseIssues), not in production.
